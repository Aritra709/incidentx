# IncidentX: Autonomous IT Incident Response Agent - Detailed Implementation Plan

## 1. PROJECT OVERVIEW

**Problem Statement:** PS1 - IncidentX: Autonomous IT Incident Response Agent
**Goal:** Build an AI agent that analyzes system logs, identifies incidents, determines severity, and recommends remediation actions.
**Approach:** Multi-stage pipeline with specialized tools for log ingestion, error detection, classification, severity assessment, and report generation.

## 3. DETAILED MODULE SPECIFICATIONS

### 3.1 Log Ingestion Module (`log_ingestion/`)

**Input Formats:**
- **TXT**: Plain text logs (syslog, application logs)
- **JSON**: Structured logs (ELK, Datadog, CloudWatch format)
- **CSV**: Exported logs with headers

**Parsing Strategy:**
```
TXT: Regex-based extraction (timestamp, level, service, message)
JSON: Direct field mapping (timestamp, level, service, message, metadata)
CSV: Header-based column mapping
```

**Output Schema:**
```python
LogEntry:
  - raw_text: str
  - timestamp: datetime
  - level: Enum[DEBUG, INFO, WARN, ERROR, CRITICAL, FATAL]
  - service: str
  - message: str
  - metadata: Dict[str, Any]
  - source_file: str
  - line_number: int
```

**Key Functions:**
- `parse_file(file_path: Path) -> List[LogEntry]`
- `parse_text(text: str, format: str) -> List[LogEntry]`
- `detect_format(file_path: Path) -> LogFormat`

### 3.2 Log Preprocessor (`preprocessor/`)

**Responsibilities:**
- Timestamp normalization (ISO 8601)
- Service name standardization
- Message cleaning (remove PII, normalize IDs)
- Time-window segmentation
- Deduplication

**Key Functions:**
- `normalize_timestamps(entries: List[LogEntry]) -> List[LogEntry]`
- `standardize_services(entries: List[LogEntry], mapping: Dict) -> List[LogEntry]`
- `segment_by_time_window(entries: List[LogEntry], window_minutes: int) -> List[List[LogEntry]]`
- `deduplicate(entries: List[LogEntry]) -> List[LogEntry]`

### 3.3 Error Detection & Classification (`classifier/`)

**Error Categories:**
```
INFRASTRUCTURE:     DATABASE_CONNECTION, NETWORK_TIMEOUT, DISK_FULL, MEMORY_EXHAUSTION, CPU_THROTTLING
APPLICATION:        NULL_POINTER, UNHANDLED_EXCEPTION, VALIDATION_ERROR, AUTH_FAILURE, RATE_LIMIT
DEPENDENCY:         EXTERNAL_API_DOWN, THIRD_PARTY_TIMEOUT, MESSAGE_QUEUE_BACKUP
CONFIGURATION:      MISSING_CONFIG, INVALID_CONFIG, FEATURE_FLAG_ERROR
SECURITY:           UNAUTHORIZED_ACCESS, INJECTION_ATTEMPT, BRUTE_FORCE, CERTIFICATE_EXPIRED
```

**Detection Methods:**
1. **Rule-based**: Regex patterns for known error signatures
2. **ML-based**: Fine-tuned classifier for log level + message
3. **Hybrid**: Rules first, ML for ambiguous cases

**Key Functions:**
- `detect_errors(entries: List[LogEntry]) -> List[ErrorEvent]`
- `classify_error(message: str, level: str) -> ErrorCategory`
- `extract_error_signature(message: str) -> str`

**Output Schema:**
```python
ErrorEvent:
  - log_entry: LogEntry
  - category: ErrorCategory
  - signature: str
  - confidence: float
  - matched_pattern: Optional[str]
```

### 3.4 Pattern Correlation Engine (`correlator/`)

**Correlation Strategies:**
1. **Temporal**: Errors within time window (default: 5 min)
2. **Service-based**: Same service, related errors
3. **Causal**: Known cause-effect patterns (DB down → API timeout)
4. **Session/Trace ID**: Same request trace

**Known Causal Patterns:**
```
DATABASE_CONNECTION_ERROR  ──▶  API_TIMEOUT, QUERY_FAILED, CONNECTION_POOL_EXHAUSTED
NETWORK_TIMEOUT            ──▶  SERVICE_UNAVAILABLE, CIRCUIT_BREAKER_OPEN
DISK_FULL                  ──▶  LOG_WRITE_FAILURE, CACHE_WRITE_FAILURE, BACKUP_FAILURE
MEMORY_EXHAUSTION          ──▶  OOM_KILLER, GC_OVERHEAD, SERVICE_CRASH
AUTH_FAILURE (spike)       ──▶  BRUTE_FORCE_DETECTED, ACCOUNT_LOCKOUT
```

**Key Functions:**
- `correlate_errors(errors: List[ErrorEvent], window_minutes: int) -> List[IncidentCluster]`
- `apply_causal_rules(clusters: List[IncidentCluster]) -> List[IncidentCluster]`
- `identify_root_cause(cluster: IncidentCluster) -> RootCauseAnalysis`

**Output Schema:**
```python
IncidentCluster:
  - id: str
  - errors: List[ErrorEvent]
  - time_range: Tuple[datetime, datetime]
  - affected_services: List[str]
  - root_cause: Optional[RootCauseAnalysis]
  - pattern_type: Enum[TEMPORAL, SERVICE, CAUSAL, TRACE]

RootCauseAnalysis:
  - primary_cause: ErrorEvent
  - contributing_factors: List[ErrorEvent]
  - confidence: float
  - reasoning: str
```

### 3.5 Severity Assessment (`severity/`)

**Severity Matrix:**
| Impact Scope | User Impact | Data Loss Risk | Recovery Time | Severity |
|-------------|-------------|----------------|---------------|----------|
| Single service | Minimal | None | < 5 min | LOW |
| Multiple services | Some users | None | 5-30 min | MEDIUM |
| Core service | Many users | Possible | 30 min - 2 hr | HIGH |
| Platform-wide | All users | Likely | > 2 hr | CRITICAL |

**Assessment Factors:**
- Number of affected services
- Error rate (errors/minute)
- User-facing impact
- Data integrity risk
- Recovery complexity
- Business criticality of affected services

**Key Functions:**
- `assess_severity(cluster: IncidentCluster, context: SystemContext) -> SeverityLevel`
- `calculate_impact_score(cluster: IncidentCluster) -> float`
- `get_service_criticality(service: str) -> CriticalityLevel`

**Output Schema:**
```python
SeverityAssessment:
  - level: Enum[LOW, MEDIUM, HIGH, CRITICAL]
  - score: float  # 0-100
  - factors: Dict[str, float]
  - justification: str
```

### 3.6 Knowledge Base (`knowledge_base/`)

**Structure:**
```
knowledge_base/
├── remediation_rules.yaml     # Pattern → Remediation mapping
├── runbooks/                  # Detailed procedures
│   ├── database_connection.md
│   ├── api_timeout.md
│   └── ...
├── service_catalog.yaml       # Service metadata, criticality, contacts
└── error_catalog.yaml         # Error signatures, descriptions
```

**Remediation Rule Schema:**
```yaml
- pattern: "DATABASE_CONNECTION_ERROR"
  severity_threshold: "MEDIUM"
  actions:
    - immediate:
        - "Check database server status"
        - "Verify connection pool configuration"
        - "Check network connectivity to DB"
      automated: true
    - investigation:
        - "Review slow query logs"
        - "Check for connection leaks"
        - "Analyze connection pool metrics"
      automated: false
    - resolution:
        - "Restart database service if needed"
        - "Scale connection pool"
        - "Fix application connection handling"
      automated: false
  runbook: "database_connection.md"
  escalation: "DBA on-call"
```

**Key Functions:**
- `get_remediation(category: ErrorCategory, severity: SeverityLevel) -> RemediationPlan`
- `get_runbook(pattern: str) -> str`
- `get_service_info(service: str) -> ServiceInfo`

### 3.7 Incident Report Generator (`reporter/`)

**Report Sections:**
1. **Executive Summary** - One-paragraph overview
2. **Incident Details** - ID, timestamp, duration, severity
3. **Root Cause Analysis** - Primary cause, contributing factors
4. **Affected Services** - List with impact description
5. **Timeline** - Chronological event sequence
6. **Remediation Plan** - Immediate, investigation, resolution steps
7. **Evidence** - Relevant log excerpts with timestamps
8. **Prevention Recommendations** - Long-term fixes

**Output Formats:**
- Markdown (human-readable)
- JSON (machine-readable)
- HTML (dashboard integration)

**Key Functions:**
- `generate_report(cluster: IncidentCluster, assessment: SeverityAssessment, remediation: RemediationPlan) -> IncidentReport`
- `export_markdown(report: IncidentReport) -> str`
- `export_json(report: IncidentReport) -> str`
